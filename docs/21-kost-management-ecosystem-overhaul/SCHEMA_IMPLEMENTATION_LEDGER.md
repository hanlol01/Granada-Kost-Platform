# KMO Schema Implementation Ledger

Status: **LIVING IMPLEMENTATION TRUTH**

This ledger separates committed design/source from database application,
reconciliation, automated verification, and runtime consumer evidence. It does
not authorize migration execution.

## 1. Status Vocabulary

Only these schema-delivery statuses are used in this ledger:

- `PLANNED`
- `SOURCE_IMPLEMENTED`
- `COMMITTED_NOT_MIGRATED`
- `MIGRATED_DEVELOPMENT`
- `BACKFILLED`
- `RECONCILED`
- `AUTOMATED_VERIFIED`
- `RUNTIME_DEFERRED`
- `RUNTIME_VERIFIED`
- `LEGACY_COMPATIBILITY`
- `DEPRECATED`

`MIGRATED_DEVELOPMENT` requires evidence from the canonical development
database. A committed SQL file, manifest entry, disposable database, or contract
test is not sufficient.

## 3. Migration Evidence Phases

These phases are independent and must not be collapsed into one status:

| Phase                      | Required proof                                                                                                  |
| -------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Migration source committed | Exact SQL bytes exist in a reviewed commit.                                                                     |
| Manifest verified          | Filename, checksum, sentinels, ordering, and replay behavior pass focused contracts.                            |
| Disposable proof           | First apply, immediate replay, rollback, and reconciliation pass on an isolated database.                       |
| Canonical application      | Operator proves exact connected development database, executes once, and records pre/post objects and checksum. |
| Backfill                   | Expected rows are created or mapped with deterministic counts and no silent ambiguity.                          |
| Reconcile                  | Required mismatch queries produce reviewed zero or explicitly bounded legacy outcomes.                          |
| Runtime consumer           | Authorized API/UI reads and writes prove the migrated authority without compatibility drift.                    |

Read-only ledger reconciliation on 2026-08-03 found migration records 001–028
in the current development database, including the flexible-term/Booking-Fee

without an active lease and 26 ownership records not yet representable.

## 4. Update Protocol

1. The executor proposes the affected ledger rows and supplies source, migration,
   disposable, reconciliation, and consumer evidence separately.
2. The reviewer proves the final source delta and assigns
   `AUTOMATED_VERIFIED`; the executor cannot self-award it.
3. The source commit may advance `SOURCE_IMPLEMENTED` or
   `COMMITTED_NOT_MIGRATED`, never `MIGRATED_DEVELOPMENT`.
4. A separately authorized operator applies a migration to the exact canonical
   development database and records pre/post evidence.
5. Backfill and reconciliation statuses advance only from their own evidence.
6. Runtime smoke advances only consumer runtime status. It does not rewrite
   migration history.
7. Compatibility authorities are removed only after zero-use evidence and an
   approved rollback boundary; then they may become `DEPRECATED`.
